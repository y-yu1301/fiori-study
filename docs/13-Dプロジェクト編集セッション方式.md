# Dプロジェクト：編集セッション方式による一括編集

List Report の**絞り込み結果の全件**を、Object Page の明細テーブルで行ごとに編集し、
1回の保存でまとめて確定し、そのまま元データへ書き戻すサンプルです。

アプリC（`docs/12`）と目的は同じですが、**作り方が違います**。
C で問題になった「検索条件を画面から画面へ持ち回る」という発想そのものをやめています。

## プロジェクト

| | |
|---|---|
| CAP Java | `D-cap` （port **4007**） |
| UI5 / Fiori Elements | `D-ui5` （port **8085**） |
| DB | H2 インメモリ（`db/data/*.csv` から起動時に再構築、購買申請 120件） |
| 認証 | mock users：`admin` / `user1` / `user2`（パスワードはユーザー名と同じ） |

---

## 1. 起動手順

ターミナルを2つ使います（devcontainer 内で実行してください）。

```bash
# ターミナル1：バックエンド（OData を 4007 で提供）
cd D-cap/srv && mvn spring-boot:run

# ターミナル2：フロント（画面を 8085 で提供、/odata は proxy で 4007 へ）
cd D-ui5 && npm install && npm start
```

ブラウザで <http://localhost:8085> を開きます。
最初に Basic 認証のダイアログが出るので `user1` / `user1` で入ってください
（mock users を有効にしているためです）。

バックエンドだけを確認したいとき：

```bash
curl -u user1:user1 'http://localhost:4007/odata/v4/BulkEditService/PurchaseRequests?$top=3'
```

## 2. 動作確認シナリオ

1. **絞り込む**
   画面を開くと、申請日には**本日を含む今後60日**が最初から入っています（必須項目・範囲のみ。§6参照）。
   そこへ `Status = SUBMITTED`、`Department = IT` などを足して Go。
2. **まとめて編集**
   テーブル右上の「まとめて編集」を押す。
   → サーバが編集セッションを1件作り、Object Page へ自動で遷移します。
   → 明細テーブルには**画面に見えていた行だけでなく、条件に合致する全件**が並びます。
3. **行ごとに編集して保存**
   遷移直後の Object Page は**表示モード**です（Fiori の標準動作）。
   右上の「編集」を押して編集モードへ。数量・単価・備考を**行ごとに違う値**で入力し、「保存」。
   → 1回の保存で全行が確定し、**そのまま元の購買申請へ書き戻されます**。
   → 「更新 n件 / 変更なし m件 / 競合 k件 / エラー j件」というメッセージが出ます。
   → 明細の「反映結果」列が色付きで更新されます。
4. **確認**
   ブラウザの戻るで List Report に戻ると、購買申請が更新されています。
5. **URL 直開き**
   Object Page の URL をコピーして F5、あるいは新しいタブで開き直しても同じ内容が出ます。
   （条件を画面の外に持っていないため、URL のキーだけで画面が再現できます）

### 競合を体感する

1. `user1` で一括編集セッションを作り、Object Page を編集モードにする（まだ保存しない）
2. 別のブラウザ（シークレットウィンドウ）で `user2` として、対象の購買申請を1件だけ更新する
   例：`curl -u user2:user2 -X PATCH 'http://localhost:4007/odata/v4/PurchaseService/PurchaseRequests(<ID>)' -H 'Content-Type: application/json' -d '{"remark":"先に更新"}'`
3. `user1` に戻って値を変えて「保存」を押す
   → その1行だけ `CONFLICT` になり、**他の行は正常に書き戻されます**

### 他人のセッションが見えないことを確認する

`user2` でログインして `Sessions` を読むと、`user1` が作ったセッションは一覧にも出ず、
URL を直接叩いても 404 になります（`@restrict` の `createdBy = $user` が効いています）。

## 3. なぜ「編集セッション方式」なのか

### やりたいこと

「Object Page に、List Report の絞り込み結果の全件を出したい」。

ところが Fiori Elements の Object Page は、**URL のキー1件を表示する画面**です。
「37件の集合」を URL で表現する場所がありません。ここが問題の本質です。

### 素直だが破綻する方法：条件を毎リクエスト運ぶ

アプリC は、検索条件を `sessionStorage` に保存し、Object Page の明細テーブルの
`beforeRebindTable` で読み直して `$filter` を差し替える方式でした。
条件を HTTP ヘッダーに載せる派生形もあります。これには次の問題があります。

| 問題 | 何が起きるか |
|---|---|
| 状態がブラウザに残る | 前回の条件が残り、別の画面や再読込で「意図しない集合」が出る |
| URL と画面が一致しない | F5・ブックマーク・共有で再現できない（キーは同じでも中身が変わる） |
| タイミングに依存する | 「条件が入る前にテーブルが読まれる」順序問題が起き、リトライループを書く羽目になる |
| 条件が無いときの扱いが曖昧 | 「値が入っている方を使う」といったフォールバック分岐が増え、全件更新の事故につながる |
| 標準機能から外れる | FE 内部コントロールを `byId()` で掴むなど、バージョン更新で壊れる実装になる |

### アプリDの方法：集合を代表する1件を先に作る

**「集合」に ID を与えてしまえば、Object Page は標準のまま使えます。**

```
List Report で絞り込み
      ↓ ［まとめて編集］
prepareBulkEdit(criteria, search)      ← 条件をサーバへ渡すのは、この1回だけ
      ↓
BulkEditSessions を1件 INSERT ＋ 対象行を BulkEditItems へコピー
      ↓ 作ったセッションを返す
Fiori Elements が Sessions(ID) の Object Page へ自動遷移
      ↓
明細テーブルで行ごとに編集 →［保存］（Draft の標準機能でまとめて確定）
      ↓ 保存の直後（draftActivate の After ハンドラ）
競合検知・業務チェックをして元テーブルへ UPDATE
```

得られるもの：

- 画面は「キー1件を開く」という**標準の作りのまま**。特別なテーブル制御が要らない
- `sessionStorage` もカスタムヘッダーも `beforeRebindTable` も**使わない**
- URL だけで画面が完全に再現できる（F5・ブックマーク・共有が効く）
- 明細は元レコードの**コピー**なので、元データが独自の Draft を持っていても衝突しない
- 「誰がいつどの条件で何件を編集しようとしたか」がデータとして残る（監査しやすい）

トレードオフ（承知のうえで選んでいます）：

- セッションと明細という**一時データが増える**（→ 定期削除で対処。後述）
- コピーなので、**コピー後に元データが変わった行**は保存時に競合になる（→ 検知して行単位でスキップ）

### 補足：`requiresNavigation: true` は unbound action では効かない

FE のドキュメントには「アクションが返した Context へ遷移する」とありますが、
実装（`sap/fe/core/controllerextensions/EditFlow.js`）の遷移判定は次のようになっています。

```js
const oActionContext = Array.isArray(mParameters.contexts) ? ... : mParameters.contexts;
const sActionContextMetaPath = oActionContext && oMetaModel.getMetaPath(oActionContext.getPath());
if (sContextMetaPath != undefined && sContextMetaPath === sActionContextMetaPath) {
  // ここで初めて遷移する
}
```

つまり「**アクションを呼んだ元の Context のメタパス == 戻り値のメタパス**」が条件です。
unbound action には呼び出し元の Context が無いので `sActionContextMetaPath` は `undefined` になり、
**この条件は絶対に成立しません**。

`requiresNavigation` が想定しているのは「Object Page で1件に対して Copy を実行し、
同じ Entity の別の1件へ移る」といった bound action の用途です。
一覧から unbound action を呼んで別の画面へ飛ぶ、という今回の用途では機能しません。

しかも**アクション自体は成功する**ため、
「ボタンを押しても何も起きない（けれどサーバにはセッションが増えている）」という
分かりにくい症状になります。

そこで `D-ui5/webapp/ext/BulkEditHandler.ts` では、戻り値からセッションIDを読み、
公開APIで明示的に遷移しています。

```ts
const result = await api.getEditFlow().invokeAction(ACTION_NAME, { ... });
const sessionId = result?.getObject()?.ID;

await api.getRouting().navigateToRoute("SessionObjectPage", {
  key: `ID=${sessionId},IsActiveEntity=true`   // Draft 有効なのでキーは2つ
});
```

`navigateToRoute` は manifest.json の `routes[].name` と `pattern` を使う公開APIです
（パターン `Sessions({key}):?query:` の `{key}` に上の文字列が入ります）。

### 補足：一覧と明細の並び順を揃える

`UI.LineItem` は「どの列を出すか」しか決めません。並び順を書かないと `$orderby` が付かず、
**DB が返した順＝不定**になります。一覧と明細で並びが違うと
「どの行の値を直したのか」を目で追えなくなるため、両方に `UI.PresentationVariant` の
`SortOrder` を付けて申請番号の昇順に固定しています。

Object Page 側は、Facet の Target を `@UI.LineItem` ではなく
**`items/@UI.PresentationVariant`** にする必要があります（LineItem を直接指すと
並び順の指定を渡す場所がないため）。

```cds
UI.Facets: [{ $Type: 'UI.ReferenceFacet', Target: 'items/@UI.PresentationVariant' }]
```

一方で **manifest.json の `controlConfiguration` のキーは `@UI.LineItem` のまま**にします。
FE のコンバータ（`sap/fe/core/converters/controls/Common/DataVisualization.js`）が

```js
annotationPath: `${baseVisualizationPath}${firstViz.value}`   // → items/@UI.LineItem
```

のように PresentationVariant を LineItem のパスへ解決してから
`getManifestControlConfiguration(visualizationPath)` を引くためです。
ここを `@UI.PresentationVariant` に変えると、テーブル設定
（ResponsiveTable 指定など）が**丸ごと無視されます**。

| 書く場所 | 指すもの |
|---|---|
| CDS の `UI.Facets` の `Target` | `items/@UI.PresentationVariant`（並び順を渡すため） |
| manifest の `controlConfiguration` のキー | `items/@com.sap.vocabularies.UI.v1.LineItem`（FE が解決した後のパス） |

### 補足：画面からの並べ替え（personalization）に必要な2つの設定

テーブル右上の歯車から並べ替え・列の増減を行う仕組み（MDC の personalization）は、
**UI5 Flexibility（`sap.ui.fl`）の上に載っています**。
`manifest.json` の `sap.ui5/flexEnabled` が `false` だと、
歯車で並べ替えを指定しても状態が保持されず、
アノテーションで決めた初期の並び順に戻り続けます（＝「並びが固定されて変えられない」症状）。

List Report 側で `variantManagement: "Page"` を使う場合も flex が前提なので、
このアプリでは `flexEnabled: true` にしています。

```json
"sap.ui5": {
  "flexEnabled": true,
  ...
}
```

**ただし、これだけでは動きません。** flex は変更の保存先（コネクタ）を持っており、
既定値は ABAP の LREP サーバです。

```js
// sap/ui/fl/initial/_internal/FlexConfiguration.js の既定値
[{ url: "/sap/bc/lrep", connector: "LrepConnector" }]
```

ローカルの `ui5 serve` にそんなエンドポイントは無いので **404** が返り、
コンソールに次のエラーが出て並べ替えが適用されません。

```
Uncaught (in promise) Error: Not Found
  at sap/ui/fl/initial/_internal/connectors/Utils.js:33   // new Error(oRequest.statusText)
  ← sap/m/p13n/Engine.js:596  createChanges
```

そこで保存先をブラウザの localStorage に変えます（`webapp/index.html` のブートストラップ）。

```html
<script id="sap-ui-bootstrap"
  src="https://sapui5.hana.ondemand.com/1.149.1/resources/sap-ui-core.js"
  data-sap-ui-flexibility-services='[{"connector": "LocalStorageConnector"}]'
  ...>
```

属性名が**ハイフン区切り**なのが要点です。UI5 は `data-sap-ui-<name>` の `<name>` を
`_camelize`（`-x` → `X`）して設定キーにするため、
`data-sap-ui-flexibilityServices` と書くと HTML が小文字化して
`sapUiFlexibilityservices` となり、本来のキー `sapUiFlexibilityServices` に一致しません。

> ここで localStorage を使うのは「画面の見た目の設定」の保存先としてであり、
> 業務の検索条件をブラウザに持たせているわけではありません（アプリCの方式とは別物）。
> 並べ替えの設定をリセットしたいときは、ブラウザの localStorage を消してください。

### 保存＝元データへの書き戻し（ボタンは1つだけ）

Object Page のボタンは「保存」だけです。
保存すると Draft が確定し、**その直後に元の購買申請へ書き戻されます**。

```java
@After(event = SessionsDraftActivateContext.CDS_NAME, entity = "BulkEditService.Sessions")
public void applyOnSave(SessionsDraftActivateContext context) { ... }
```

当初は「保存」と「反映（bound action）」の2段階でしたが、やめました。
保存したのに元データが変わらない状態はユーザーから見て理解しにくく、
反映を押し忘れたまま離脱する事故が起きるためです。
**押し忘れという失敗そのものを無くす**方が、ボタンで気づかせるより確実です。

書き戻しの粒度は行単位のままなので、失うものはありません。

| 行の状態 | applyStatus | 元データ |
|---|---|---|
| 値を変えた | `APPLIED` | UPDATE する |
| 何も変えていない | `UNCHANGED` | **触らない** |
| 他の人が先に更新していた | `CONFLICT` | 触らない（他の行は進む） |
| 業務チェック違反 | `ERROR` | 触らない（他の行は進む） |

「変更なしの行は触らない」のは重要です。保存のたびに全行を UPDATE すると、
編集していないレコードの `modifiedAt` まで動いてしまい、
他の人の編集セッションが不要に競合します。

## 5. 条件の受け渡し形式（JSON AST）

フロントとバックエンドは、次の形**だけ**をやり取りします。

```jsonc
// 単一条件
{ "kind": "cond", "path": "status", "operator": "EQ", "value1": "SUBMITTED" }

// 範囲（BETWEEN）
{ "kind": "cond", "path": "requestDate", "operator": "BT",
  "value1": "2026-01-01", "value2": "2026-06-30" }

// 論理結合（and:true なら AND、false なら OR）
{ "kind": "group", "and": true, "filters": [ /* cond または group */ ] }
```

- 許可する演算子：`EQ` `NE` `GT` `GE` `LT` `LE` `BT` `Contains` `StartsWith` `EndsWith`
- 許可する項目：`CriteriaTranslator.ALLOWED_PATHS` に定義したものだけ
- ネスト最大5階層、条件最大200件
- **上記に反したら 400 エラーで即座に拒否**します。無視も、全件へのフォールバックもしません

サーバ側は文字列で SQL を組み立てず、`CQL.get(path).eq(value)` のように
**クエリをオブジェクトとして**組み立てます（SQL インジェクションの余地がない書き方）。

## 6. 日付フィルタの既定値・必須・範囲限定（コードを書かずに設定する）

申請日フィルタは次のようにしてあります。**JavaScript は1行も書いていません。**

| やりたいこと | 手段 | 書く場所 |
|---|---|---|
| 申請日を**必須**にする | `Capabilities.FilterRestrictions.RequiredProperties` | `D-cap/srv/annotations.cds` |
| **範囲でしか**絞り込めなくする | `FilterExpressionRestrictions.AllowedExpressions: 'SingleRange'` | `D-cap/srv/annotations.cds` |
| **本日を含む今後60日**を初期値にする | `filterFields.requestDate.settings.defaultValues` | `D-ui5/webapp/manifest.json` |

CDS 側：

```cds
annotate BulkEditService.PurchaseRequests with @(
  Capabilities.FilterRestrictions: {
    RequiredProperties           : [ requestDate ],
    FilterExpressionRestrictions : [
      { Property: requestDate, AllowedExpressions: 'SingleRange' }
    ]
  }
);
```

manifest 側（List Report の `controlConfiguration` 内）：

```json
"@com.sap.vocabularies.UI.v1.SelectionFields": {
  "filterFields": {
    "requestDate": {
      "settings": {
        "defaultValues": [
          { "operator": "NEXTXDAYSINCLUDED", "values": [60] }
        ]
      }
    }
  }
}
```

### なぜこれで済むのか

`Edm.Date` かつ `AllowedExpressions` が `SingleRange` / `SingleValue` の項目には、
Fiori Elements の**セマンティック日付演算子**が自動で有効になります
（今月 / 先週 / 今後X日 …）。
`NEXTXDAYSINCLUDED` は「**本日を含む今後X日**」という*動的な*範囲なので、
「本日」を JavaScript で計算して初期値に入れる必要がありません。
画面を開いた日が変われば、範囲もその日を起点に自動で動きます。

X を取る演算子は `"values": [60]` のように**数値1つ**を渡します。
他にも `LASTXDAYSINCLUDED`（過去X日）、`THISMONTH`、`DATERANGE`（固定の範囲）などがあります。
過去方向にしたい場合は `NEXTXDAYSINCLUDED` を `LASTXDAYSINCLUDED` に変えるだけです。

### 「範囲でない場合は+60日にする」を処理として書かなかった理由

`SingleRange` にすると**単一日付そのものが選べなくなる**ため、その分岐が発生しません。

仮に「単一日付が来たら +60日 の範囲に広げる」とサーバ側や `filterSerializer` に書くと、
**List Report は1日分を表示しているのに、一括編集は60日分を掴む**という食い違いが生まれます。
「画面に見えている絞り込み結果 ＝ 編集対象」という前提が崩れるので、
広げる処理を書くのではなく、**そもそも範囲しか選ばせない**ようにしています。

### 単一日付の演算子まで完全に消したい場合

`SingleRange` でも `TODAY` のような「1日を表す範囲」の演算子は選択肢に残ります。
これも消したい場合は、同じ `settings` に `operatorConfiguration` を足してください
（`exclude: true` で個別に除外できます）。

```json
"settings": {
  "defaultValues": [ { "operator": "NEXTXDAYSINCLUDED", "values": [60] } ],
  "operatorConfiguration": [
    { "path": "key", "equals": "TODAY",     "exclude": true },
    { "path": "key", "equals": "YESTERDAY", "exclude": true },
    { "path": "key", "equals": "TOMORROW",  "exclude": true }
  ]
}
```

> サンプルデータ（`db/data/*.csv`）は、この既定の絞り込み窓に結果が出るよう
> **2026-08-12 を基準**に 2026-06-13 〜 2026-12-07 の範囲で生成してあります
> （既定の「本日〜+59日」に 40件が入ります）。
> 別の日に動かして件数が減った場合は、CSV の日付を作り直してください。

| 変えたいこと | 触る場所 |

| 一度に編集できる上限（既定500件） | `application.yaml` の `bulk-edit.max-items` と `D-ui5/webapp/ext/BulkEditHandler.ts` の `MAX_ITEMS`（**必ず両方**） |

## 8. 既知の制約

- **同じレコードを複数セッションに含めた場合**
  先に保存した方が勝ちます。後から保存した側はその行が `CONFLICT` になり、スキップされます
  （データが壊れることはありませんが、後勝ちにはなりません）。
- **保存後もセッションは残ります**
  「いつ何を書き戻したか」の記録として残す方針です。一度も保存されていないセッションだけが
  24時間後に自動削除されます。
- **セッション削除時、Draft の残骸が残ることがあります**
  掃除処理はアクティブなセッションを削除します。編集途中（Draft）のまま放置された場合の
  Draft 行の掃除は、このサンプルでは扱っていません。
- **保存は何度でも押せます**
  前回 `APPLIED` になった行は控えの更新日時も更新済みなので、自分自身とは競合しません。
  `CONFLICT` / `ERROR` の行を直して保存し直す運用を想定しています。
- **List Report と Object Page は同じサービス（BulkEditService）を見ています**
  Fiori Elements の1アプリは1つの OData サービスにバインドされるため、
  「一覧は PurchaseService、編集は BulkEditService」という分け方は標準機能ではできません。
  `PurchaseService` は「一括編集と無関係に元データを扱う API」として別に用意してあります。
