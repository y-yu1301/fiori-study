## 2. データの形は7回変わる

同じ「検索条件」が、layer をまたぐたびに姿を変えます。**どの形で見ているかを意識しないと、
「値が入っていない」の原因を取り違えます。**

| # | 形 | 例 | 触る場所 |
|---|---|---|---|
| 1 | 画面の入力値 | 場所=東京、日付=2026/08/01〜08/31 | FilterBar（コードで触らない） |
| 2 | Condition | `{ operator:"DATERANGE", values:["2026-08-01","2026-08-31"] }` | `applyConditionMap`（版差の保険） |
| 3 | UI5 Filter | `{ sPath:"businessDate", sOperator:"BT", oValue1:Date, oValue2:Date }` | `applyFilter` / `collectFilters` |
| 4 | 業務DTO | `{ location:"東京", fromDate:"2026-08-01", toDate:"2026-08-31", status:"OPEN" }` | `sessionStorage`（唯一の正） |
| 5a | HTTP Header | `X-Search-Condition: %7B%22location%22%3A%22%E6%9D%B1...` | `changeHttpHeaders` → `readSearchCondition` |
| 5b | OData `$filter` | `location eq '東京' and businessDate ge 2026-08-01 ...` | `createODataFilters` → 受信CQN |
| 6 | CQN | `{"SELECT":{"from":...,"where":[{"ref":["location"]},"=",{"val":"東京"}]}}` | `rewriteBulkItemsQuery` / `createWhere` |
| 7 | 表示文字列 | `searchPeriod = "2026/08/01～2026/08/31"` | `afterReadWorkItems` / `periodText()` |

**注意点**

- 3→4 で `Date` を `yyyy-MM-dd` に切っています（`toText`）。ここを飛ばすと CAP の `Edm.Date` と噛み合いません
- 4→5a で `encodeURIComponent`。HTTP ヘッダーに日本語をそのまま載せられないためで、CAP 側は `URLDecoder.decode(..., UTF_8)` で戻します。**片側だけ変えると文字化けします**
- 5a と 5b は**同じ条件の二重経路**です（Fが意図的に残している課題）
- 6 は文字列連結ではなくオブジェクトとして組み立てています（`createWhere`）

## 3. フェーズ別の流れ

### フェーズ0：起動と初期化

```text
index.html（LocalStorageConnector を指定）
  → Component.js（sap.fe.core.AppComponent）
    → manifest.json の models."" から ODataModel を1つ生成
      → routing の routes/targets を登録
        → 初期ルート ":?query:" → List Report
```

**注意点**

- ODataModel は**アプリ全体で1つ**です。List Report・Object Page・明細テーブルが同じ Model を共有します。
  → `changeHttpHeaders()` はこの1つに対する設定なので、**一度付けると以降の全リクエストに乗ります**（⚠️一覧へ戻っても付いたまま）
- `flexEnabled: true` と `index.html` の `LocalStorageConnector` はテーブルの並べ替え・列設定（personalization）用です。
  ローカルには `/sap/bc/lrep` が無いため、これを指定しないと歯車での設定が 404 で失敗します
- 拡張コントローラは manifest の `sap.ui5.extends.extensions.sap.ui.controllerExtensions` で FE の標準コントローラに紐づきます。
  クラス名（`f.retry.edit.ui.ext.controller.ListReportExt`）と `controllerName` が一致していないと**静かに呼ばれません**

### フェーズ1：List Report で検索する

| 順 | 誰が | 何をする | データの形 |
|---|---|---|---|
| 1 | ユーザー | FilterBar に入力して Go | 形1 |
| 2 | FE | 条件を正規化（セマンティック日付の展開など） | 形2/3 |
| 3 | **`ListReportExt#onBeforeRebindWorkItems`** | `collectFilters` → `applyFilter` で DTO 化し `sessionStorage` へ保存 | 形3→4 |
| 4 | FE | READ を発行 | 形5b |
| 5 | CAP | 標準 READ（ハンドラなし） | 形6→SQL |
| 6 | CAP | **`afterReadWorkItems`** が発火 ⚠️ | 形7 |
| 7 | FE | 一覧を描画 | — |

`onBeforeRebindWorkItems` の中身は「読む」だけで、条件を**追加しません**。一覧の検索は標準の `$filter` で走ります。

**注意点**

- 条件の取得元は **`event` 側（そのREADに実際に使われる Binding 情報）を優先**し、取れないときだけ `api.getFilters()` を使います。
  FilterBar の入力値を直接読むと、FE が正規化した後の値とズレます（例：「今月」は展開済みでないと CAP に渡せない）
- `applyFilter` は対応表（`location EQ` / `status EQ` / `businessDate BT・GE・LE・EQ`）に無い条件を**無視**します。
  「一覧では絞れているのに明細が全件」の第一候補がこれです（詳細ログに `★無視した条件` が出ます）
- 条件を1つも拾えなかった場合、DTO は空 `{}` になります。**空＝全件が編集対象**なので `console.warn` を出しています
- ⚠️ `sessionStorage` は**単一キー**です。複数の検索結果を同時に保持できません（タブを分けても同一オリジンで共有されます）
- ⚠️ 手順6：`afterReadWorkItems` は一覧READでも発火します。Object Page を開いた後に戻って再検索すると、
  **残ったままの古いヘッダー**で一覧READが飛び、各行に古い virtual 値が入ってモデルにキャッシュされます

### フェーズ2：行クリックから Object Page へ

```text
行クリック
  → FE 標準Navigation（manifest の navigation.WorkItems.detail.route）
    → URL が #/WorkItems(<ID>) へ変わる
      → ObjectPage コンポーネントが生成され、ルートContextが作られる
```

**注意点**

- Fは行クリックに手を入れていません（Eは `onBeforeNavigation` でヘッダーを設定しています）。
  そのため**ヘッダー設定の開始が Object Page 側まで遅れます**。これがタイミング問題の根本原因です
- URL に入るのはキーだけです。検索条件は URL に含まれないため、
  ⚠️ **F5・ブックマーク・URL共有では条件が復元されません**（`sessionStorage` が残っていれば同一ブラウザでは動きます）

### フェーズ3：Object Page ヘッダー側

```text
ObjectPageExt#onBeforeBinding(context)            ← ルートContextが画面へセットされる直前
  ├ ログ: context.getPath() / getObject()          ← ここで値があれば一覧から引き継いだ古い値 ⚠️
  ├ _fHeaderRetryToken を進める（世代管理）
  └ applyHeaderWithRetry(controller, context, token, 1)
       ├ トークンが最新でなければ何もしない（古いNavigationのタイマーを無効化）
       ├ loadSearchCondition()            … 形4
       ├ encodeURIComponent(JSON...)      … 形5a
       ├ model.changeHttpHeaders({...})
       │    ├ 成功 → 次へ
       │    └ 例外（通信中）→ 150ms 後に自分を再呼び出し（最大40回 ≒ 6秒）⚠️
       └ context.requestRefresh()          … ヘッダー付きで再READ ⚠️2往復目
            └ ログ: refresh後の virtual項目
```

CAP 側:

```text
GET /WorkItems(<ID>)
  → 標準READ（キーで1件）
    → afterReadWorkItems(context, rows)
         readSearchCondition(context)
           ├ ヘッダーなし → Optional.empty()（virtual項目は空のまま。何も詰めない）
           └ ヘッダーあり → decode → JSON → SearchCondition レコード
                └ rows へ searchLocation / searchPeriod / searchStatus を put
```

**注意点**

- **virtual 項目は DB 列ではありません**。`row.put()` でレスポンスに載せているだけで、レコードの中身ではありません。
  保存対象にもなりません（`EDITABLE_FIELDS` に含めていない）
- ⚠️ `changeHttpHeaders()` は「これから飛ぶリクエスト」にしか効きません。すでに飛んだ／キャッシュから返された READ には効きません
- ⚠️ ODataModel V4 のキャッシュキーは**リソースパス＋クエリオプション**で、**HTTP ヘッダーは含まれません**。
  つまりモデルから見て「条件Aで読んだ `WorkItems(123)`」と「条件Bで読んだ `WorkItems(123)`」は同一で、再READが起きません。
  → **これが「古い条件が表示され続ける」直接の原因です**
- `requestRefresh()` はそのキャッシュを捨てて再READさせる**救済**です。解決ではないので、
  ヘッダー設定が最後まで失敗すれば refresh も走らず、ヘッダー表示は空のままになります
- ヘッダーが無いとき CAP 側は**意図的に何もしません**。「前回の条件を覚えて代用する」処理を入れると、
  表示している条件と実際の集合がズレても気づけなくなるためです
- リトライのトークン管理は必須です。リトライ中に一覧へ戻って別の行を開くと、
  古いタイマーが古い `context` を refresh してしまいます

### フェーズ4：Object Page 明細側

```text
ルートContextが確定
  → 明細テーブルの相対ListBindingが組まれる
    → ObjectPageExt#onBeforeRebindBulkItems(event)
         ├ ログ: bindingParams.filters（追加前）
         ├ loadSearchCondition()        … 形4
         ├ createODataFilters()          … 形4→3（GE + LE の2本に分解）
         ├ appendFiltersToRebind()       … bindingParams.filters へ push（既存とAND）
         └ ログ: bindingParams.filters（追加後）
      → GET /WorkItems(<ID>)/bulkEditItems?$filter=...&$count=true
```

CAP 側:

```text
onReadBulkItems(context)                        @On READ WorkItemService.WorkItemBulkItems
  ├ ログ: 受信CQN（加工前）
  ├ readSearchCondition(context)                … ヘッダーを読む
  ├ rewriteBulkItemsQuery(context, headerCondition)
  │    ├ CQN を JSON として読み込む
  │    ├ from を WorkItemService.WorkItemBulkItems へ差し替え
  │    │    ★Navigation由来の「選択した1行だけ」という制約を外すため
  │    ├ ヘッダーあり → where を createWhere() で作り直す（$filter を上書き）
  │    └ ヘッダーなし → where を触らない（$filter がそのまま効く＝フォールバック）
  ├ db.run(Select.cqn(...).inlineCount())       … $count=true に応えるため
  └ ログ: source=HEADER / ODATA_FILTER、返却件数
```

**注意点**

- `@On` で自前実行しているのは `from` を差し替える必要があるからです。標準のままだと Navigation の制約で1行しか返りません
- `orderBy` / `limit` / `columns` は受信CQNのまま残します。並べ替え・ページングは標準に任せ、
  差し替えるのは「どの Entity Set を読むか」と「業務のWHERE」だけに限定しています
- `inlineCount()` を忘れると、FE のテーブルが件数を得られず「もっと読む」が正しく動きません
- ⚠️ 明細は**その場で再検索した結果**です。List Report を表示した後に DB が変われば、明細の集合も変わります
  （Dのように「見えていた集合」を固定していません）
- ✅ 明細側が安定して正しく出るのは、条件が `$filter`＝**キャッシュキーに含まれる形**で渡っているからです。
  ヘッダー側だけ古くなる非対称は、ここの違いから生じています
- 明細には**選択した行自身も含まれます**（同じ DB テーブルの投影なので）

### フェーズ5：編集する

```text
「編集」ボタン → 標準Draft（WorkItems は @odata.draft.enabled）
  ├ ルート … Draft 行が作られる（IsActiveEntity=false）
  └ 明細テーブル … WorkItemBulkItems は非Draft投影
        セル変更 → PATCH /WorkItemBulkItems(<ID>)
                     → beforeUpdateBulkItem（ログのみ）
                     → ★Active行が即座に更新される
```

**注意点**

- ⚠️ **明細の変更は「保存」を待たずに DB へ入ります**。非Draft投影を直接更新しているためです。
  そのため編集をキャンセルしても明細の変更は戻りません。Draft の「編集中は隔離される」性質が明細側には効いていません
- ヘッダー側は `editableHeaderContent: false` なので編集対象外です。virtual 項目も書き戻し先がありません
- 明細で編集できる項目は `WorkItemsHandler.EDITABLE_FIELDS` と `WorkItemBulkItems` の `UI.LineItem` の**両方**に依存します

### フェーズ6：保存する

```text
「保存」→ Draft Activate
  → 内部で UPDATE WorkItems（IsActiveEntity=false）が発生
      → beforeUpdateWorkItemRoot(draftRootRow)
           ├ IsActiveEntity が false 以外なら何もしない
           ├ 同じ ID の Active 行を読む
           ├ ログ: EDITABLE_FIELDS ごとに before（Draft側）/ after（Active側）
           └ Active の値を Draft側の更新データへ上書きコピー
  → Active へ確定
```

**注意点**

- ⚠️ この同期処理が無いと、**明細テーブルで変更した選択行だけが古い値に巻き戻ります**。
  ルートの Draft は「編集モードに入った時点の値」を持っているため、それが Active を上書きしてしまうからです
- 「保存後に一部の行だけ値が戻る」症状が出たら、`[F-DEBUG] Draft同期 <項目> before/after` を確認します
- Draft と非Draft投影が同じテーブルを見ている構造そのものが原因なので、同期はその辻褄合わせです
  （Dは明細を**コピー**にすることでこの問題自体を発生させていません）

## 4. なぜ Header と `$filter` のタイミングは合わないのか

Fを保守するうえで最も分かりにくいのがこの点なので、独立した節にします。

### `X-Search-Condition` に値が入るのは1箇所だけ

```text
ObjectPageExt.controller.ts
  override.routing.onBeforeBinding          … Object Page のルートContextセット直前
    └ applyHeaderWithRetry(...)
         ├ loadSearchCondition()            … sessionStorage から DTO を読む
         ├ encodeURIComponent(JSON...)      … ヘッダー用の文字列にする
         └ model.changeHttpHeaders({ "X-Search-Condition": encoded })   ★ここだけ
              └ 失敗（通信中）→ 150ms 後に自分を再呼び出し（最大40回）
```

値の元をたどると `ListReportExt#onBeforeRebindWorkItems` の `sessionStorage.setItem(...)` です。
つまり **条件を書き出す時刻と、ヘッダーへ載せる時刻は別**です。
そして **削除している場所はありません**（一度設定するとモデルに残り続けます）。

### ズレる理由：貼り付け先が違う

実装の詰めの問題ではなく、2つが**別のものに紐づいている**ためです。

| | `$filter`（明細側） | `X-Search-Condition`（ヘッダー側） |
|---|---|---|
| 貼り付け先 | **その Binding／そのリクエスト** | **ODataModel（アプリ全体で1つの可変状態）** |
| 設定する場所 | `onBeforeRebindBulkItems` → `appendFiltersToRebind` | `applyHeaderWithRetry` → `changeHttpHeaders` |
| 効果の範囲 | この1リクエストだけ | 呼んだ**後に組まれる全リクエスト** |
| 同期／非同期 | 同期。呼ばれた直後にそのリクエストが組まれる | 実質非同期。通信中は例外 → リトライ |
| 失敗しうるか | しない（イベントが来た時点で必ず間に合う） | する（間に合わない／付きすぎる） |
| リクエストとの対応 | 1対1で保証される | **保証されない** |

`$filter` は「このリクエストに、この条件を」と言えます。
ヘッダーは「モデルの現在の設定値が、たまたまその瞬間に組まれたリクエストへ乗る」だけです。
**1対1の対応関係がそもそも存在しない**ので、揃えようとすると必ずタイミング勝負になります。

### ズレは2方向に出る

```text
時間 →
  ┌ List Report の $batch（まだ飛んでいる）
  │
  │   onBeforeBinding ─ changeHttpHeaders() → 例外「pending requests」
  │        ↓ 150ms リトライ…
  │
  └─完了
        ルートREAD が組まれて飛ぶ ←── ★ヘッダー無し（付かなすぎ）
             リトライ成功 → changeHttpHeaders()
                requestRefresh() → ルートREAD 2回目 ←── ヘッダー有り
                     明細READ ←── ヘッダー有り ＋ $filter（二重経路）
  …ブラウザバックで一覧へ
        一覧の再検索READ ←── ★前回の条件のヘッダーが付いたまま（付きすぎ）
```

| 方向 | 何が起きるか | 症状 |
|---|---|---|
| 付かなすぎ | ヘッダーが必要なリクエストに間に合わない | ヘッダー側が空 |
| 付きすぎ | 不要なリクエスト（一覧の再検索）に古い条件が乗る | 古い virtual 値がキャッシュに残り、あとで表示される |

さらに OData V4 は複数 Binding の要求を `$batch` にまとめます。
**ルートREADと明細READが同じ `$batch` に入れば、両者は必然的に同じヘッダー値を共有します。**
リクエストごとに別の値を持たせる余地はありません。

### 対処は「揃える」ではなく「揃える必要をなくす」

リトライ回数を増やす・待ち時間を延ばす・`refresh` を足す方向は、1対1の対応が無い以上
どこまでやっても確率の問題として残ります。効くのは次の3つです。

| # | 方針 | 具体策 | 消える症状 |
|---|---|---|---|
| ① | リクエストごとに変わる値を、モデル全体の状態に置かない | 条件は `$filter`（または `$`/`@` で始まらないカスタムクエリオプション）で送る。V4 の Binding にリクエスト単位のカスタムヘッダー指定は無く、`changeHttpHeaders` しか無い ＝ **ヘッダーはリクエスト単位の情報を運ぶ道具ではない** | タイミングのズレそのもの |
| ② | ヘッダー側の表示を通信から外す | `sessionStorage` の DTO を JSONModel に入れ、Custom Header Facet でバインドする | 付かなすぎ・付きすぎ・キャッシュ由来の古い値 |
| ③ | ヘッダーを残すなら、値が変わらない設計にする | モデルがアイドルなタイミングで1回だけ設定（アプリEの `onBeforeNavigation`）。不要な場面では**必ず削除**（Eは一覧の rebind で消している） | 付きすぎ（付かなすぎも大幅に軽減） |

③だけではキャッシュキーにヘッダーが入らない性質が残るため、②との併用が確実です。
①を突き詰めると、条件を「運ぶもの」から「あるもの」に変えるアプリDの編集セッション方式になります。

## 6. 症状 → 原因 → 確認箇所

| 症状 | 主な原因 | 最初に見る場所 |
|---|---|---|
| ヘッダーが空 | ルートREADがヘッダー設定より先に飛んだ | CAP `WorkItems READ header=なし` ／ FE `③OP header (試行n)` |
| ヘッダーが古い条件 | ヘッダーがキャッシュキーに入らず再READされない。一覧から引き継いだ値 | FE `③OP onBeforeBinding` の「モデルにある値」、`refresh前/後` |
| 明細が全件出る | 条件を拾えず DTO が空。または対応外の演算子 | FE `①` 加工後DTO、`★無視した条件` |
| 明細の件数が一覧と違う | 5a と 5b の条件がズレている／DBが変わった | CAP `source=` と `返却件数` |
| 明細が1件しか出ない | `from` 差し替えが効いていない | CAP `Rewritten bulk-items CQN` |
| 保存後に一部だけ値が戻る | Draft ルートが Active を上書き | CAP `Draft同期 before/after` |
| 文字化け | エンコード／デコードの不一致 | CAP `加工前: ヘッダーの生の値` と `加工中: デコード後のJSON` |
| キャンセルしても明細が戻らない | 非Draft投影を直接更新する構造（仕様） | フェーズ5の注意点 |

## 7. 項目を1つ増やすときに触る場所（全部）

条件に `assignee`（担当者）を足す場合の例です。**片方だけ直すと二重経路が食い違います。**

| # | ファイル | 変更内容 |
|---|---|---|
| 1 | `F-cap/srv/work-item-service.cds` | `UI.SelectionFields` に `assignee` を追加 |
| 2 | `F-ui5/.../SearchCondition.ts` | `SearchCondition` 型に `assignee` を追加 |
| 3 | 同上 `applyFilter` | `assignee EQ` の分岐を追加（対応表に無いと無視される） |
| 4 | 同上 `createODataFilters` | `assignee` の Filter 生成を追加（5b 経路） |
| 5 | `F-cap/.../WorkItemsHandler.java` の `SearchCondition` レコード | フィールドを追加 |
| 6 | 同上 `createWhere` | `addCondition(where, "assignee", "=", ...)` を追加（5a 経路） |

3・4 と 5・6 のどちらかを忘れると、「ヘッダー経路では絞れるが `$filter` 経路では絞れない（またはその逆）」という
**再現条件が分かりにくい不整合**になります。二重経路方式の維持コストがここに現れます。

## 8. この流れを前提にした改善の入口

Fの弱点は3か所に集中しています。改善する場合の入口を整理しておきます。

| 弱点 | 入口 | 効果 |
|---|---|---|
| ヘッダー設定が間に合わない | 設定を行クリック時（`onBeforeNavigation`）へ前倒しする（アプリE方式） | リトライが不要になる |
| ヘッダー表示が古い／空 | 表示を通信で取らず、`sessionStorage` の DTO を JSONModel にしてヘッダーへバインド | 原因1・2ごと消える。変更範囲はヘッダー周りだけ |
| 集合が固定されない／URL再現不可 | 条件から「集合を代表する1件」を作る（アプリD方式） | タイミング・古いデータ・F5 がまとめて解決 |

上2つは現場コードへの適用コストが小さく、3つ目は作り直しの機会がある場合の選択肢です。
