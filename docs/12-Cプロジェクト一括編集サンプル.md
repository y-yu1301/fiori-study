# Cプロジェクト一括編集サンプル

このサンプルは、List Reportで検索した同じ業務レコード群を、Object Page本文のテーブルにも表示してまとめて編集する構成です。

## 目的

List Reportでは編集せず、Object Page右上の編集ボタンから編集モードに入り、List Reportと同じ条件で絞り込まれた複数レコードを編集します。

CAP Java側ではBefore READで`context.getCqn()`を読み、`where`条件から日付範囲を抽出・加工できるポイントを用意しています。
Object Page本文の`bulkEditItems` READでは、親Object PageのIDに縛られたCQNをそのまま標準処理へ流さず、On READで検索条件ベースのCQNを独自実行して結果を返します。

## データモデル

`Campaigns`がList ReportにもObject Page本文にも表示する同じ編集対象レコードです。
Object Page右上の編集ボタンから編集モードに入れるよう、Draft有効かつ更新可能にしています。
作成・削除は`Capabilities.InsertRestrictions.Insertable: false`ではなく、`UI.CreateHidden` / `UI.DeleteHidden`で画面上から隠しています。
Draft編集では内部的にDraft側の作成処理が必要になるため、Entity自体をinsert不可にすると`Entity 'CampaignService.Campaigns' is not insertable`になる可能性があります。

```cds
entity Campaigns {
  name            : String;
  keyword         : String;
  targetDate      : Date;
  status          : String;
  assignee        : String;
  plannedQuantity : Integer;
  actualQuantity  : Integer;
  comment         : String;
  virtual filterNote : String;

  bulkEditItems : Association to many CampaignBulkItems;
}
```

`bulkEditItems`はDBテーブル上の自己関連ではありません。
Draft Rootである`Campaigns`自身を本文テーブルに自己関連で出すと、Draft編集時に同じIDのDraft行を複数作ろうとして一意制約に当たります。
そのため、Object Page本文のテーブルは、同じDBテーブルを読む別投影`CampaignBulkItems`へナビゲートします。
UI5側でList Reportと同じ`$filter`を差し込むため、Object Page本文にも同じ条件の業務レコードが表示されます。

## 画面側の流れ

1. List Reportで`targetDate`、`keyword`、`status`、`assignee`などを指定して検索する。
2. 表示されたレコードの1件を押してObject Pageへ遷移する。
3. List ReportのテーブルREAD直前に`ListReportExt.controller.ts`の`onBeforeRebindCampaigns`が呼ばれる。
4. そのREADで実際に使われる`collectionBindingInfo` / `bindingParams`内のFilterを`sessionStorage`へ毎回上書き保存する。
5. 行クリック時はFiori Elementsの標準ナビゲーションでObject Pageへ遷移する。ここでは検索条件を読み直さない。
6. Object Pageの`ObjectPageExt.controller.ts`が`sessionStorage`から検索条件を復元する。
7. `bulkEditItems`テーブルREAD直前に`onBeforeRebindEditableRows`が呼ばれる。
8. 復元した`filters`を`sap.ui.model.Filter`に戻して`addFilter`する。
9. CAP Javaには`CampaignBulkItems` READの通常の`$filter`として届く。
10. `CampaignsHandler.beforeReadCampaignBulkItems`がObject Page本文READのCQNを受け取り、filter条件をログ・加工ポイントとして扱う。
11. `CampaignsHandler.onReadCampaignBulkItems`が、元CQNの`where`全体を残したまま、親IDではなく`CampaignBulkItems`を読むCQNへ差し替える。
12. 差し替えたCQNを`PersistenceService`で独自実行し、そのResultを画面へ返す。
13. FEのテーブルREADは`$count=true`付きで来るため、独自実行する`Select`には`inlineCount()`を付ける。

List Reportの日付条件は、UI5のバージョンやFilterBarの状態によって`sap.ui.model.Filter`ではなく`conditions` / `filterConditions`形式に入ることがあります。
ただし現在の主経路は、FilterBar状態ではなく、List ReportテーブルREAD直前のrebindイベントから実際のbinding filterを読むことです。
`extensionAPI.getFilters()`や`conditions`は、rebindイベントからFilterを取れなかった場合の同一画面状態の表現差吸収としてのみ使います。
Object Page遷移直前の`onBeforeNavigation`では保存しません。ここで読み直すと、検索直後のタイミングによって前回条件で`sessionStorage`を上書きしてしまうためです。

## sessionStorageに保存する検索条件の例

```json
{
  "filters": [
    {
      "sourcePath": "targetDate",
      "path": "targetDate",
      "operator": "BT",
      "value1": "2026-08-04",
      "value2": "2026-08-12"
    }
  ],
  "search": "summer",
  "summary": "対象日: 2026-08-04 - 2026-08-12 / 検索ワード: summer"
}
```

`filters`はREAD用です。
`summary`はログ確認や将来の表示拡張用です。現在のObject Pageには検索条件ヘッダーFacetを出していません。
List Report側は、一覧テーブルのREAD直前に`sessionStorage`の検索条件を毎回上書きします。
Object Page側はURL queryや保存済み別キーへフォールバックせず、このキーだけを読みます。
ただし、List Reportが条件なしで全件表示している場合は、空の`filters`を「全件表示」という明示的な検索状態として保存します。
ブラウザの`sessionStorage`はハードリロードでは消えないため、アプリ起動時に`Component.js`でこのキーを削除します。
これにより、Object Pageを直接リロードした時に前回の検索条件を誤って再利用しません。

## CAP Javaで見る場所

対象ファイル:

```text
C-cap/srv/src/main/java/customer/c_filter_edit/CampaignsHandler.java
```

Before READ入口:

```java
@Before(event = CqnService.EVENT_READ, entity = "CampaignService.CampaignBulkItems")
public void beforeReadCampaignBulkItems(CdsReadEventContext context) {
    String cqnText = context.getCqn().toString();
    FilterSummary summary = extractTargetDateFilter(cqnText);
}
```

このBeforeでは以下を行います。

- Object Page本文テーブルREADに届いた`$filter`を確認する
- `targetDate`の日付範囲を抽出する
- 抽出した値を使って関連テーブルを検索する
- 必要ならCQNへ業務条件を追加するための加工ポイントにする

独自READ入口:

```java
@On(event = CqnService.EVENT_READ, entity = "CampaignService.CampaignBulkItems")
public Result onReadCampaignBulkItems(CdsReadEventContext context) {
    String rewrittenCqn = rewriteBulkItemsCqn(context.getCqn().toString());
    return db.run(Select.cqn(rewrittenCqn).inlineCount());
}
```

このOn READでは以下を行います。

- Object Page本体のID条件に縛られないCQNへ差し替える
- `targetDate`だけでなく、`keyword`、`status`、`assignee`、検索ワード由来のfilterもwhere全体として維持する
- `$count=true`要求に対応するため、独自実行する`Select`に`inlineCount()`を付ける
- 独自取得したResultをそのまま画面へ返す

このサンプルでは、抽出した条件を`filterNote`というvirtual項目に入れて画面に返します。

## 編集確認

Object Pageの本文テーブルで`actualQuantity`や`comment`を変更して保存すると、変更行ごとにUPDATEが発生します。

CAP Java側では以下のBefore UPDATEでログ確認できます。

```java
@Before(event = CqnService.EVENT_UPDATE, entity = "CampaignService.CampaignBulkItems")
public void beforeUpdateCampaignBulkItems(CdsData row) {
    logger.info("CampaignBulkItems BEFORE UPDATE data: {}", row);
}
```

## 確認ポイント

List Reportで`targetDate = 2026-08-04..2026-08-12`を指定して検索し、Object Pageへ遷移します。

CAPログに以下のようなREADが出れば成功です。

```text
GET /Campaigns(...)/bulkEditItems?$filter=targetDate ge 2026-08-04 and targetDate le 2026-08-12 ... 200
```

Before READログでは以下のようにwhereが確認できます。

```text
CampaignBulkItems BEFORE READ CQN: ... where=[targetDate >= 2026-08-04 and targetDate <= 2026-08-12] ...
CampaignBulkItems extracted filter summary: targetDate 2026-08-04 .. 2026-08-12
```

このあとOn READ内で差し替えCQNを独自実行するため、選択したObject Page本体が8/5のレコードでも、本文テーブルは8/1-8/15の検索条件で再取得されます。
このREADは`$count=true`付きで呼ばれるため、独自実行するCQNに`inlineCount()`がないと`The query result misses a value for $count`になります。
また、条件なし検索も正常ケースとして扱うため、元CQNに`where`が無い場合も同じOn READ経路で全件取得します。
sessionStorageに検索条件が無い場合は、古い条件や別経路へフォールバックせずエラーにします。
一方、List Report自体が条件なしで全件表示している場合は、保存した検索コンテキストの`filters`が空の正常ケースとして扱い、Object Page本文も全件READへ差し替えます。

List Reportに出ていたSato、Suzuki、Tanakaなどの同じ`Campaigns`レコードが、Object Page本文にも同じ条件で表示されます。

## 注意点

このサンプルは「Beforeでfilterを読めること」を見せるため、CQNの文字列表現から日付条件を抽出しています。
本番ではCAP JavaのCQN APIでwhere句を構造的に走査する実装に置き換える方が堅牢です。

Object Page本体READはキー指定の単一Entity READです。
複数件編集対象はObject Page本文の別投影テーブルとして表示しています。

Object Pageの「ヘッダー」Facetは定義せず、本文にはラベルなしの一括編集リストだけを出す構成です。
